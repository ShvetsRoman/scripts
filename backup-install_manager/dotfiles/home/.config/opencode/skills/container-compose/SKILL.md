# Container Compose

## Призначення

Цей Skill містить спільні правила роботи з контейнерними проєктами:

- Podman та Podman Compose;
- Docker Engine та Docker Compose V2;
- Compose Specification;
- Containerfile і Dockerfile;
- контейнери, образи, мережі, томи;
- healthcheck, secrets, конфігурації;
- systemd та автоматичний запуск контейнерів.

Використовуй ці правила під час роботи з відповідними проєктами.

## Контекст середовища

Основне середовище користувача:

- Arch Linux;
- Zsh;
- Podman 6.2.0;
- podman-compose 1.6.0.

Не припускай, що Docker Engine встановлений або запущений.

Перед вибором команд визначай фактично доступний інструментарій. Не змішуй Docker і Podman без пояснення причин.

## Вибір Compose-реалізації

1. Для Podman спочатку розглядай `podman compose`.
2. Враховуй, що `podman compose` є оболонкою над зовнішнім Compose-провайдером.
3. Визначай, який саме провайдер використовується: `podman-compose` або `docker-compose`.
4. Не припускай повної сумісності `podman-compose` з Docker Compose V2.
5. Для Docker використовуй Compose V2 — `docker compose`.
6. Не використовуй застарілий `docker-compose` як основний інтерфейс без обґрунтування.
7. Якщо конфігурація залежить від специфіки провайдера, чітко зазначай це.

## Робочий процес

Перед будь-якими змінами:

1. Визнач мету завдання.
2. Перевір структуру відповідного проєкту.
3. Вивчи наявні Compose-файли, Containerfile/Dockerfile та конфігурації.
4. Визнач залежності, мережі, томи, порти та змінні середовища.
5. Вияв ризики й несумісності.
6. Склади конкретний план змін.
7. Дочекайся погодження користувача перед змінами.

Не змінюй файли, які не стосуються поставленого завдання.

## Правила Compose

- Дотримуйся Compose Specification.
- Не додавай застарілі параметри без необхідності.
- Не дублюй конфігурацію між сервісами без причини.
- Використовуй зрозумілі назви сервісів, мереж і томів.
- Для залежностей сервісів враховуй реальну готовність сервісу, а не лише факт запуску контейнера.
- Додавай healthcheck там, де він має практичну користь.
- Не публікуй порти без потреби.
- Враховуй різницю rootless і rootful режимів Podman.
- Перевіряй права доступу до bind mounts.
- Не припускай однакової поведінки volume, network та user namespace у Docker і Podman.

## Безпека

- Не записуй паролі, токени та приватні ключі безпосередньо в Compose-файли.
- Використовуй `.env` лише для відповідних конфігураційних значень, не як сховище секретів.
- Не виводь значення секретів у звіти.
- Не відкривай `.env`, `.env.*`, приватні ключі та файли облікових даних без дозволу.
- Не додавай секрети до Git.
- Не запускай контейнери з `privileged: true` без обґрунтування.
- Не використовуй `network_mode: host` без пояснення наслідків.
- Не монтуй системні каталоги хоста без необхідності.
- Мінімізуй права контейнерів.
- Не використовуй `latest` у критичних конфігураціях без обґрунтування.

## Деструктивні операції

Без окремого погодження не виконуй:

- `podman system reset`;
- `docker system prune`;
- `podman volume rm`;
- `docker volume rm`;
- видалення контейнерів або образів;
- видалення каталогів із даними;
- очищення баз даних;
- перезапуск або зупинку робочих сервісів;
- застосування змін до системного systemd.

Перед такою операцією поясни:

1. Що саме буде видалено або змінено.
2. Які дані можуть бути втрачені.
3. Які сервіси можуть бути недоступні.
4. Чи можна відновити попередній стан.

## Команди та виконання

Перед запуском команд:

- пояснюй їхнє призначення;
- відокремлюй діагностику від зміни стану;
- не маскуй помилки через `|| true`;
- не запускай довгі або фонові процеси без потреби;
- не виконуй мережеві операції без відповідного погодження;
- не використовуй `sudo` для обходу проблем із правами без аналізу причини.

Враховуй дозволи OpenCode. Цей Skill не надає додаткових прав агенту.

## Перевірка конфігурації

Після погоджених змін перевіряй конфігурацію відповідним Compose-провайдером.

Для Podman:

```bash
podman compose config
```

Для Docker:

```bash
docker compose config
```

Використовуй лише команду, відповідну фактично обраному провайдеру.

Не запускай `up`, `down`, `build`, `pull` або інші операції зі зміною стану, якщо користувач просив лише аналіз конфігурації.

## systemd

Під час налаштування автоматичного запуску:

- визначай, чи потрібен user або system service;
- для rootless Podman враховуй user systemd;
- не створюй дублікати наявних unit-файлів;
- перевіряй залежності та порядок запуску;
- враховуй поведінку після перезавантаження;
- не вмикай і не запускай unit без погодження.

## Якість результату

Після роботи надавай:

1. Короткий опис проблеми або мети.
2. Перелік перевірених файлів.
3. План і фактично виконані зміни.
4. Повний вміст змінених конфігураційних файлів.
5. Команди перевірки.
6. Результати перевірок.
7. Відомі обмеження та невирішені проблеми.

Використовуй статуси:

- PASS — перевірка успішна;
- FAIL — виявлена помилка;
- SKIP — перевірку не виконано;
- TIMEOUT — перевірка перевищила час очікування.

Не називай проєкт готовим, якщо критичні перевірки не виконані.

## Правила взаємодії

- Відповідай українською.
- Коментарі в конфігураційних файлах пиши українською, якщо формат це дозволяє.
- Пояснюй технічні рішення зрозуміло.
- Для змін коду та конфігурацій надавай повні файли, а не окремі фрагменти.
- Не вигадуй результати команд або перевірок.
- Не відхиляйся від основної мети завдання.
