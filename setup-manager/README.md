# Setup Manager V3.0 — Unified Core

Єдина точка входу для встановлення програм і роботи з dotfiles. У V3.0 **Installer і Dotfiles Manager використовують спільне ядро `lib/core.sh`** для синхронізації, порівняння, захисних резервних копій та recovery. Реєстри конфігів **залишилися окремими**.

## Швидкий старт

```bash
./setup.sh doctor
./setup.sh test
./setup.sh smart --dry-run cli shell
./setup.sh
```

Не запускайте `setup.sh` через `sudo` — інсталятор сам запитує потрібні права.

## Команди

```bash
./setup.sh packages --dry-run cli       # План установки
./setup.sh smart --dry-run cli shell    # Smart Setup
./setup.sh backup changed              # Backup змінених dotfiles
./setup.sh restore                     # Відновлення (з підтвердженням)
./setup.sh status                      # Загальний стан
./setup.sh verify                      # Загальна перевірка
./setup.sh doctor                      # Діагностика
./setup.sh test                        # Автоматичні тести
./setup.sh dotfiles                    # Повне меню Dotfiles Manager
```

## Де вносити зміни

- `install-packages/modules/*.sh` — пакети й конфіги інсталятора, кожен модуль окремо.
- `dotfiles-manager/config/dotfiles.conf` — **незалежний** реєстр резервного копіювання dotfiles.
- `config/setup.conf` — параметри головного меню та Smart Setup.
- `lib/core.sh` — **спільна** реалізація файлових операцій; при додаванні нової програми редагувати не потрібно.

## Схема резервного копіювання

| Режим | Джерело | Місце призначення | Правила |
|---|---|---|---|
| `installer` | Чинний конфіг на ПК | `install-packages/backups/` | Захисна копія перед заміною, без перезапису існуючого backup |
| `dotfiles` | Чинний конфіг на ПК | `dotfiles-manager/dotfiles/` | Синхронізація через rsync за окремим реєстром |
| `recovery` | Чинні конфіги | `dotfiles-manager/dotfiles-recovery/` | Захисні знімки перед restore (існуючий recovery-механізм збережений) |

**Увага:** sync каталогу з `--delete` може прибирати файли в цільовій директорії, яких немає у джерелі. Перед першим використанням виконайте `--dry-run`, перегляньте реєстри й зробіть зовнішню копію важливих даних.

## Архітектура

`setup.sh` координує підсистеми; `lib/core.sh` є єдиним файловим ядром; `install-packages/` відповідає за пакети, права й налаштування служб; `dotfiles-manager/` відповідає за реєстр dotfiles, меню архівів, Git та життєвий цикл recovery. Збережено сумісні команди V2.1.

## Перевірки

```bash
bash -n setup.sh lib/core.sh
bash tests/run-tests.sh
./setup.sh test
```

Тести не заміняють випробування на реальній Arch Linux. ShellCheck запускайте окремо, якщо встановлений.


## Виведення у термінал та dry-run

- Кожен модуль починається з окремого заголовка `Модуль: id — Назва`.
- Встановлені пакети виводяться поспіль без зайвих порожніх рядків.
- Якщо в модулі немає AUR-пакетів, виводиться відповідне повідомлення; якщо всі AUR-пакети наявні — повідомлення про це.
- Backup та копіювання показують короткий ID конфігу (наприклад `fzf`) замість довгого шляху.
- У `--dry-run` не створюються каталоги; повідомлення містять `[DRY-RUN]` і не стверджують, що конфіг вже встановлено або backup зроблено.
- Фактичні шляхи можна знайти у реєстрах і плані команд копіювання.

### Уточнений вивід модулів

- Заголовок: `[STEP] Встановлення модуля: docker — Docker`.
- Завершення: `[OK] Завершено встановлення модуля: docker — Docker`.
- Зовнішні та GitHub-програми мають власний заголовок після AUR; `superfile` більше не виглядає AUR-пакетом.
- Окремі реєстри конфігурацій збережено.


### Покращене логування конфігів

Для кожного конфігу тепер показуються повні шляхи «Звідки» та «Куди» під час захисного backup і копіювання. Успішні операції мають повідомлення «Захисний backup: NAME виконано.» та «Конфіг: NAME скопійовано.». У `--dry-run` виводиться лише план майбутніх дій — без хибних повідомлень про успіх. Якщо джерело відсутнє, попередження містить ідентифікатор конфігу та шлях.

## Форматування Doctor та Smart Setup

- `doctor` відокремлює підсумок порожніми рядками; у TTY кількість модулів виділена зеленим, ненульові помилки — червоним, ненульові попередження — помаранчевим. При `NO_COLOR=1`, перенаправленні в файл або `TERM=dumb` кольори вимикаються.
- У Smart Setup є відступ після підтвердження встановлення і між завершенням модуля та запитом про додаткову синхронізацію.
- Якщо погодитися на синхронізацію, запускається `dotfiles-manager backup changed`: тільки шляхи з **окремого реєстру Dotfiles Manager**, напрямок `HOME → dotfiles-manager/dotfiles`. Це **не** новий захисний backup або tar-архів; існуючі конфіги у dotfiles можуть змінитися. Якщо обрати `n`, дія пропускається.


## Maintenance — 12 операцій

Запуск: `./setup.sh maintenance` або пункт 7 головного меню.

1–2. Збереження всіх або лише змінених dotfiles.
3–5. Створення, перегляд і відновлення архівів. Перед відновленням обов'язково створюється захисний архів поточного сховища.
6–9. Перегляд, відновлення, видалення та очищення recovery. Перед відновленням — захисна копія наявних HOME-шляхів. Старі recovery видаляються після підтвердження з урахуванням ліміту 5.
10. Видалення резервних копій Installer старших за 30 днів.
11. Видалення журналів Installer старших за 30 днів.
12. Перегляд розмірів резервних копій та вільного місця.

Строк очищення 10–11 змінюється змінною `SETUP_MAINTENANCE_DAYS=45` у `config/setup.conf` (за замовчуванням 30). Перед видаленням програма показує всі шляхи й запитує підтвердження. Реєстри конфігів залишаються незалежними.

### Уточнення виводу Smart Setup і Doctor

- Підсумок Doctor підсвічує весь показник **модулів** зеленим; ненульові **помилки** — червоним, **попередження** — помаранчевим.
- ANSI-кольори використовуються тільки при виводі у термінал; `NO_COLOR=1` вимикає їх.
- Перед запитом про синхронізацію Dotfiles Manager повідомлення виводяться через кольоровий `log_info`, потім додається порожній рядок. У журналі ці повідомлення залишаються без ANSI-кодів.


## Вимкнення захисного backup Installer

За замовчуванням `CONFIG_BACKUP=true` у файлі `install-packages/config/installer.conf`.
Щоб постійно вимкнути захисне копіювання існуючих конфігів перед їхнім перезаписом,
встановіть `CONFIG_BACKUP=false` у цьому файлі.

Для одного запуску використовуйте:

```bash
./setup.sh smart --no-backup cli
./setup.sh smart --dry-run --no-backup cli
./setup.sh install --no-backup cli
```

Параметр `--no-backup` вимикає **тільки захисні резервні копії Installer**.
Він не вимикає синхронізацію Dotfiles Manager на окремий запит і не змінює
механізми recovery при відновленні. **Увага:** існуючі конфіги можуть
бути перезаписані без захисної копії.


## Порівняння конфігів (виправлено)

Status, Diff і Verify тепер ігнорують відмінності лише у timestamp, правах та власнику.
Позначення відносно HOME: `[NEW]` — файл є в HOME, але відсутній у dotfiles;
`[DEL]` — файл є в dotfiles, але відсутній у HOME; `[CHANGED]` — змінений вміст.
`[ERROR]` позначає помилку порівняння. `Diff` виводить ці позначення поряд із unified diff.

### Пояснення статусів файлів

У Status та Diff кожна зміна супроводжується українським описом:

```text
[CHANGED] .config/helix/config.toml - вміст файлу змінено
[NEW]     .config/yazi/theme.toml - файл є в HOME, але відсутній у dotfiles
[DEL]     .config/eza/old-config.yml - файл є в dotfiles, але відсутній у HOME
```



## Єдина бібліотека UI

`lib/ui.sh` — єдине джерело кольорів, повідомлень і заголовків для
`setup.sh`, `install-packages/install.sh` і `dotfiles-manager/dotfiles-manager.sh`.

Доступні функції: `log_info`, `log_ok`, `log_warn`, `log_error`,
`log_step`, `log_debug`, `print_header`. Старі назви функцій прибрані; використовуйте лише стандартні `log_ok` і `log_warn`.

Кольори відображаються лише в терміналі (TTY), вимикаються через `NO_COLOR=1`
або для перенаправленого виводу; журнали залишаються без ANSI-послідовностей.
Не визначайте `log_*` або кольори в модулях повторно.


## Стандартизація меню та назв файлів

- `lib/ui.sh` — єдині кольори, `log_*` і `print_header`.
- `install-packages/lib/menu.sh` — меню Installer (попередня назва `ui.sh`).
- `install-packages/lib/common.sh` — загальні утиліти Installer, без повторного підключення UI.
- `dotfiles-manager/dotfiles-manager.sh` і його тести підключають `../lib/ui.sh` напряму.
- Зайві обгортки `install-packages/lib/colors.sh` і `dotfiles-manager/lib/logging.sh` видалено.
- Усі інтерактивні головні та сервісні меню використовують `print_header`.


### Статичний аналіз ShellCheck

```bash
sudo pacman -S --needed shellcheck
./tests/test-shellcheck.sh

# Або напряму (з аналізом source):
find . -type f -name '*.sh' -print0 | xargs -0 -r shellcheck -x --source-path=SCRIPTDIR -S style
```

Зауваження `SC1091` для локальних динамічних `source` задокументовані та
вимикаються тільки в відповідних точках входу/тестах; інші правила залишаються активними.

### UI: окремі кольори потоків і стійкість журналу

- `log_error` визначає ANSI-колір за `stderr` (дескриптор 2) незалежно від `stdout`.
- `NO_COLOR` і `TERM=dumb` вимикають ANSI в обох потоках.
- `_ui_emit` має окремі оголошення `local`, а помилка `_setup_log_sink` повідомляється в `stderr`, не зупиняючи основну команду. Повідомлення не надсилається повторно до sink, тому рекурсії немає.
- Регресійний тест: `bash tests/test-ui-streams.sh`.

### Кольорові повідомлення

`lib/ui.sh` автоматично вмикає кольори лише коли відповідний потік (stdout/stderr) підключений до термінала, `TERM` не `dumb`, а `NO_COLOR` не задано. Для діагностики: `printf 'TERM=%s NO_COLOR=%s\n' "${TERM:-<не задано>}" "${NO_COLOR:-<не задано>}"`.

- `SETUP_COLOR=auto ./setup.sh` — автоматичний режим (типовий).
- `SETUP_COLOR=always ./setup.sh` — примусово використовувати ANSI у pipe/redirect; не перевизначає `NO_COLOR` чи `TERM=dumb`.
- `SETUP_COLOR=never ./setup.sh` — без кольорів.
- `unset NO_COLOR; export TERM=xterm-256color` — приклад відновлення умов для кольорів у справжньому терміналі (не змінюйте `TERM` без потреби).

Тест `tests/test-ui-streams.sh` навмисно симулює збій журналу та перевіряє попередження без показу його на екран.

### Навігація в меню

У кожному інтерактивному меню діє спільне правило:

- `0` — назад на попередній рівень. У головному меню повертає до оболонки, оскільки вищого рівня немає.
- `00` — повний вихід із Setup Manager, навіть із вкладеного меню Installer або Dotfiles.

Якщо Installer чи Dotfiles запущені автономно, `00` закриває лише відповідний окремий процес.
CLI-команди (`./setup.sh smart`, `./setup.sh backup` тощо) не змінено.
Регресійний тест: `bash tests/test-menu-navigation.sh`.
